# Runbook — Observability & Alerts (Stage 3)

## Overview
This runbook explains the alerts generated by the `alert_watcher` service that watches Nginx `access.json` logs and posts alerts to Slack.

### Alert types
1. **Failover detected** (e.g., `BLUE → GREEN`)
   - Meaning: The pool header in Nginx logs changed; traffic is observed from the other pool. This usually means a failover or manual switch occurred.
   - Operator action:
     1. Check Nginx config and `ACTIVE_POOL` value.
     2. Inspect the target pool container logs (`docker-compose logs app_green` or `app_blue`).
     3. Check health checks (HTTP 200 responses) for primary container.
     4. If failover is unexpected, check recent deploys/cron/automation that might toggle `ACTIVE_POOL`.
     5. If necessary, revert the active pool or bring the failing service back online.

2. **High upstream 5xx error rate**
   - Meaning: Over the sliding window (default 200 requests) the percentage of 5xx responses from upstream exceeded the configured threshold (default 2%).
   - Operator action:
     1. Identify which pool is active (failover alert or check headers).
     2. Inspect upstream application logs: `docker-compose logs app_blue` or `app_green`.
     3. Check resource usage (CPU/memory) of the app container.
     4. If a deployment caused errors, consider rolling back the deployment.
     5. If intermittent, enable `MAINTENANCE_MODE` temporarily during investigation to suppress alerts.
     6. After remediation, verify error rate returns to normal.

3. **Recovery / Silence**
   - When the error rate falls below threshold and/or pool flips back, the watcher will stop sending repeated alerts (due to cooldown). No explicit "recovery" Slack message is sent by default — check logs or look for subsequent normal metrics.

## Suppressing alerts during planned action
- Set `MAINTENANCE_MODE=true` in `.env` (and restart `alert_watcher`) to temporarily suppress alerts during maintenance windows or chaos drills.
- Alternatively, increase `ALERT_COOLDOWN_SEC` to reduce alert frequency.

## How to respond (condensed)
1. For **failover**: check which pool is receiving traffic; inspect container logs; ensure intended pool is healthy.
2. For **high error rate**: check upstream logs and health; consider scaling, rollback or restart of the app container.
3. Document steps taken and time in incident notes channel.

## Verification
- To verify alerts: run chaos drill (kill primary container) and observe Slack for a failover message.
- To test error-rate: generate HTTP 5xx from upstream and wait until the watcher posts an error-rate alert.
